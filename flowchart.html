乐高 AI 平台 · 核心流程

运营输入意图 → AI 产出成品 → 各职能只在门上 Review。节点与阶段对齐研发已在试运行的真实流水线：7 阶段 · 27 节点 · 7 道人审门。

01

核心流程总览

创意与玩法 → 视觉设计 → 技术方案 → 实现 → 上线 → 分析优化 → 下线
创意与玩法1 节点 · 0 门运营可见：全部 —— 这是运营主场
玩法路由与参数抽取流水线原名：需求分析 运营自己确认无人审
立项通过后自动建卡；AI 把一句话描述路由到枚举玩法并预填参数，运营对照需求点逐条确认，这一步不设人审门——玩法是枚举的、参数有 schema 校验，本身就是确定性的，再加一道人工没有增量信息。
合规的落点跟着变了：业务原来在这道门上把合规口径，现在改成生成时的硬约束——B 面的禁用词库与合规口径在路由阶段自动校验，命中才升级为人工。见 05。

研发原「交互与视觉定稿」（199min，全程最长的单节点）拆成风格定稿 + 页面全量生成两节点：设计要的两次确认之间必须夹着页面生成这个动作，不拆开这两道门会落在同一个节点出口，等于只确认了一次；且 199min 一个黑盒对运营等于没有进度，拆开后「卡在设计确认① · 林一 · SLA 剩 20min」才看得见、催得动。
这一段与下一段的边界就是确认②：确认②之前是设计在产出、设计在审，交付物是设计稿；之后主角换成前端 / 后端 / 策略，交付物是技术方案。研发流水线把两段合并在「方案设计」一个分组里，运营视角必须拆开——否则运营看着「方案设计」，却卡在前端席位上。
技术方案7 节点 · 2 门运营可见：阶段进度 + 卡在谁
点位说明审核前端 · 后端 · 策略 物料出图前端方案后端方案策略方案 方案定稿 方案人审各职能
点位说明是拿确认②之后的稿子产出的，所以两道设计门必须都在它之前——这也是这一段能独立成阶段的前提：它的输入是已定稿的视觉，输出是研发能直接开工的方案。
没有并进「实现」：并进去会让「实现中」这个状态骗人（运营以为在写代码，其实还在写方案文档），也会让实现段背两个交付物两道终局门。判据见 05「一个阶段 = 一个交付物 + 一个主责职能 + 一道终局门」。
注意这一段与研发分组不是一一对应：研发的「方案设计 8/8」= 我们的视觉设计 + 技术方案，对账时按此映射。
实现6 节点 · 1 门运营可见：阶段进度 + 卡在谁
前端实现后端实现策略实现 效果预览 产物人审设计验收 · 前端 · 后端 · 策略 · QA · 业务 线下测试
「效果预览」的产物真能点、跳转接真实链路，所以设计那一次验收（带真实跳转逻辑）就落在产物人审的设计席位，不必后移到上线之后——后移的话代码已经上线，驳回代价是另一个量级。这一段也是全程最长的（三方实现 + 效果预览约 107min），因此产物人审驳回必须分两档，见 05。设计若在门内改过，驳回时那份修订随之作废——这条要写在驳回弹层的代价行里。
上线5 节点 · 1 门运营可见：灰度进度 + 上线审批
代码上线 资源就位 线上零流量测试 上线人审各职能上线审核人 全量上线
上线本身是灰度：零流量验证 → 上线人审判断时机与回滚 → 才全量。旧版「分发」一格里没有灰度概念，而回滚能力正是上线审核人要判断的东西。上线人审驳回只退回本阶段起点，产物人审结论保留。

05

关键流转规则

二十四条已拍板的决策

阶段划分默认对齐研发流水线，只在主角换人时拆

运营视角的阶段默认取研发流水线的泳道及其 x/y 完成计数，不自造一套；节点与阶段由流水线定义驱动，前端不写死常量——否则研发加一个 agent，我们的原型和线上就对不上。唯一的例外是研发的「方案设计 8/8」，我们拆成视觉设计 + 技术方案两个阶段：这个分组里主责职能换了人（设计 → 前 / 后 / 策）、交付物换了种（设计稿 → 技术方案），合在一起运营会看着「方案设计」却卡在前端席位上。对账时按「研发方案设计 = 我们视觉设计 + 技术方案」映射，计数仍取流水线的。

一个阶段 = 一个交付物 + 一个主责职能 + 一道终局门

这是要不要拆 / 要不要合阶段的判据。视觉设计交付设计稿、主责设计、终局门确认②；技术方案交付四方方案与物料、主责前 / 后 / 策、终局门方案人审；实现交付能点的产物、主责研发、终局门产物人审。按这条判据，把点位与三方方案并进「实现」是不成立的——实现段会背两个交付物、两道终局门，而且「实现中」这个状态会骗人：运营以为在写代码，其实还在写方案文档。

确定性的环节不设人审门

创意与玩法这一步取消了需求人审，运营自己确认即可。理由：玩法是枚举的、参数有 schema 校验，路由结果要么落在枚举集内要么被明确拒绝，再加一道人工没有增量信息，只增加一次等待。判断标准：一道门只有在"人能给出机器给不出的判断"时才该存在；纯校验类的把关一律下沉为硬约束。

合规前移为硬约束，不设常设门

业务原来在需求人审上把合规口径，那道门取消后合规不是往后挪到产物人审，而是往前变成生成时的自动校验——B 面的禁用词库与合规口径在玩法路由阶段就跑，命中才升级为人工。往后挪的代价是等方案和代码都做完才发现问题；变成硬约束才符合「卡口自动拦截量 ↑ · 人工审阅量 ↓」那条收敛逻辑。业务在产物人审仍保留席位，但那时审的是成品表达，不是口径。

阶段名用运营语言，节点名保留流水线原名

阶段分组是我们自己划的，可以本地化成运营听得懂的说法（「需求分析」是面向 AI 的描述，运营视角叫「创意与玩法」）。节点是研发正在跑的东西，改名会造成两套口径，所以「点位说明审核」「产物人审」这类节点名一律不动。界面上凡出现节点名，就是流水线上的那个名字。

一道门 = N 个职能席位 + 一条会签规则

7 道人审门全套这同一个模型。流水线图上画成单个节点的「产物人审」，内部是多职能并行会签，不是单人审。运营视角每道门只显示三件事：通过进度（3/6）、卡在谁、催办。

第二次及以后的门只审差量

一条链路 7 道门乘上职能数，是 20 次量级的人工审核动作。这个量级下的真实后果不是流程慢，是盲签。所以：确认②只看相对确认①新增的页面态；设计验收只看相对确认②的跳转与交互态；优化人审只看相对上一次已通过版本的改动。不重复铺全量内容。

设计两次确认 + 一次验收

①核心风格确认 ②全部页面生成后确认 ③带真实跳转逻辑的验收（落在产物人审的设计席位，因为「效果预览」的产物真能点）。①未过不生成全量页面，②未过不产出点位说明——点位说明是拿确认后的稿子产出的。

产物人审驳回分两档

还原度问题（实现没做到稿子：间距、颜色、跳转接错）→ 退回实现，设计稿与方案保留，这是默认档。设计本身要改（看到真实跳转后发现流程不对）→ 退回页面全量生成，连带作废方案与实现，必须由设计显式选择，且界面要先告知代价（作废 N 个节点、约 X min）。实现段约 107min，一键全废的按钮不能存在。

驳回按门分级退回，不统一回草稿

各门退回点见 02。通则：驳回只作废本门及其下游，上游已通过结论保留。上线人审是例外——它否的是上线时机与风险，不是内容。旧版「驳回统一退回草稿并解锁」只在只有设计稿的阶段成立，放到实现之后就是灾难。

设计可在门内接棒改页，但改是捷径不是义务

设计在自己的工作台打开活动页面全貌，可以接棒与 AI 对话改这一版，也可以不改。这道门的职责仍然是判定——按判定是分钟级，按代改是小时级，所以不把代改写成设计的交付责任。改动记在设计名下、进修订号，通过时以 diff 推给运营；运营可对任一处提回改请求，但不阻塞流转（流程已经往下走了，异议只能后置补救）。上线审批那道门不给编辑入口——它判的是时机与回滚，不是内容。

机器能判定的不进人工清单

预检结论按可信度分三档：确定性判定（对比度、字号栅格、动效时长、图标来源、卡片尺寸这类读 token 或读参数即可）只展示结论，人不勾；只能给疑似（安全区压边、极端内容下的溢出截断、暗色模式实际渲染）必须人工复核，进清单；机器完全判不了（品牌调性、视觉层级、识别性、破例裁量）进清单。清单里混入机器已判准的条目 = 重复劳动 + 盲签来源。另设一条预检结论抽检随机抽 1 项让人实测核对，勾"不一致"触发规则复盘但不阻塞通过——说真话要是会卡住自己的活动，人就会改勾"一致"，抽检立刻失效。预检的盲区要在 B 面明写出来，假装全覆盖比承认盲区危险。

破例可反复申请，但要带申请次数与上次结论

运营对某条规范申请破例不限次数、不置灰入口。代价是每次申请都必须带上第几次与上次谁驳的、驳的理由原话，审阅人才判得出"他有没有回应上次的理由"。破例被准予后要记在活动上，下游 QA 与上线审核看到的是"已批准的例外"，不会当成 bug 再驳一遍。

审核超时不自动放行，也不自动换人

一期不做自动升级备份审阅人。超时后 SLA 变红，运营能催办（同一审阅人每 2 小时限一次、每次写入时间线）或撤回，没有任何自动动作。理由：自动放行等于这道门不存在，只是延迟了几小时；自动换人则需要先定清备份席位从哪来、换人还是加人、会签分母变不变，这些没定之前编一个机制比承认没有更危险。要不要加备份席位看试运行的实际超时率。

上线后原地优化，不复制新活动

已上线活动走分析优化阶段的「优化 → 优化人审」原地改。旧规则（已上线内容锁定、改动即复制成新活动重走全流程）已废：上线后调文案、调概率、换素材是运营常态，强迫复制等于逼他们绕开平台。因此「已上线」态要保留编辑入口，改完自动进入待优化确认。

每个职能两类审核人

质量审核人进点位说明 / 方案 / 产物 / 优化四道门，上线审核人只进上线人审。这样运营新建活动配 2×N 个人而不是 7×N。名册由各职能在自己工作台维护默认值，新建活动自动带出、可按活动覆盖；同一人可兼任但必须显式勾选。

策略是独立职能

不并入后端。策略有自己的方案节点、实现节点、每道门里的席位、审核人名册，以及 B 面资产（发奖与概率规则库、反作弊口径、奖品库存与发奖上限卡口）。

Agent 节点折叠，门必须冒泡

判断标准一句话：会阻塞、且需要平台外的人动手的环节，必须在运营视角可见（卡在谁 · SLA 剩多久 · 一键催办），其余一律折叠成一行进度。27 个节点里运营真正能动的只有 7 道门，且能做的动作只有催办。

界面上只说耗时与影响面，不说金额

代价一律用时间与作废范围表达：「已消耗约 50min 不可退 · 重跑还需约 107min」「作废 11 个节点 · 约 107min」。金额（单节点单价、活动总成本、预算占比）不进任何角色的界面——运营要判断的是亏多少工时、下游作废多少，把生成单价摆出来只会引出无谓的单价对比，而且它不是运营的决策变量。节点级的 $ 与 min 留在研发试运行期的调优数据里，不做成产品字段。

Agent 失败自动重试，超限才升级

中间的失败与重试对运营静默；重试次数用尽才置为「生成失败」并通知运营，失败节点支持原地重跑而不是整条重来。生成中取消 = 回空草稿，活动卡始终存在、可追溯。

主版本归运营，门内改动进修订号

发起任一人审门即锁定主版本，运营需先撤回审核才能编辑，撤回即解锁并作废该门已有结论——杜绝「审的是 A、上的是 B」。但门内的审阅人（设计）可以接棒改这一版，这类改动不动主版本，递增修订号：v1 → v1.1。结论绑定在修订版上，diff 基线是主版本，下一道门的差量以最新修订版为准。例外：分析优化阶段的优化允许在已上线态直接改，改动进入新的主版本并触发优化人审。

B 面规则变更需双人审批

资产与规则（模板硬约束、UI 规范、组件白名单、发奖概率规则、卡口）全局生效，改动影响所有在建及已上线活动，因此与活动审批链分开走双人审批。设计侧为活动执行设计 + AI 平台内容生产设计负责人；研发与策略侧待定。

立项系统只做上游约束

不把立项表单搬进来。立项通过后自动建活动卡，立项单字段（活动平台、预算、活动规模、活动周期、结束与下线时间、MRD、绑定团队、有无激励）在平台内只读，要改回立项系统改；平台反向回写活动名称、QPS 预估、生成总耗时。活动状态只由平台持有，立项系统那边只有「已立项 / 未立项」。立项门放在创意与玩法之前——预算与规模决定生成台首屏形态，拿不到就不该开始。

结束与下线是两件事

结束时间到 = 玩法停止收数据（不再产生新参与、不再出图），入口还在，进去只看得到结果页；下线时间到 = 入口撤掉，从分发资源位移除。两个时间各自可配、也都能手动触发，下线后进入退场并归档效果分析结论。
